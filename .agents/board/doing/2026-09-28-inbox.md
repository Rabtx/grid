## What

One Inbox page listing what needs the person across every project: an agent waiting for approval or
input, a turn that finished or failed while they were away, and — when GitHub is connected — review
requests and failing checks on their pull requests. Items live in the runner's SQLite, fed from the
same attention hook push notifications already use; opening the thread they point at marks them read.
The sidebar gets an Inbox entry in its top group carrying the unread count.

## Why / Context

Attention is scattered: a push notification is the only signal today, it vanishes once dismissed,
and there is no way to ask "what is waiting for me?" across projects. Board, files and pulls are all
per-project; nothing spans them. The runner already knows every moment worth interrupting someone for
— `chat.onUnwatchedAttention` in `apps/runner/src/main.ts:26`, the same call that reaches
`attentionMessage` for push.

## Proposal or Ask

- **Store:** a new `inbox_items` table in the runner's chat database (`apps/runner/src/inbox/store.ts`),
  one row per thing needing a person, keyed so the same event never lands twice. Rows carry the
  workspace, kind, project, title, body, url and `read_at`.
- **Feed:** `attentionMessage` already decides what a finished turn, a failure or a waiting approval
  deserves. Store the item from that same hook, and push as before — one decision, two sinks.
- **GitHub:** the inbox asks `gh` for `review-requested:@me` and for open pull requests with failing
  checks, per project folder that is linked. Refreshed on open, throttled, and skipped entirely
  when GitHub is not connected. Items that are gone upstream are cleared, so the list does not rot.
- **Read:** `POST /inbox/read` marks one item or everything. The console calls it when the person
  opens a thread (chat) or a pull request, and the page offers "Mark all read".
- **Console:** `/inbox`, mobile first, built from the kit only. Rows show kind, project, title, the
  line of context and a relative time; unread rows are marked. Tapping a row marks read and navigates.
- Sidebar: `Inbox` with the kit's `Count` badge in the top group.

Definition of done: a person can open one page and see everything waiting on them across projects,
tapping an item takes them there and clears it, and the sidebar count agrees with the page.

## Scope

**In scope:** the runner inbox store, routes and the feed/push wiring in `main.ts`; the console inbox
module, the `/inbox` route, and the sidebar entry.

**Out of scope:** push delivery itself (unchanged), GitHub webhooks (there is no webhook receiver;
the inbox polls), dismissing or snoozing items, marking read from a second device, and anything in
`apps/console/src/modules/github` or `settings`.

## Resolution

### Changed

- `apps/runner/src/inbox/store.ts` — `inbox_items` in the chat database, keyed by the event that
  made each row, newest first (`created_at DESC, id DESC` so two items from the same moment keep
  their order between reads), `unread`, `read` / `readAt` (a page marks every row pointing at it,
  query and all), `forgetMissing` (a GitHub refresh takes back only its own kinds, only in one
  project, and only unread rows), and read rows pruned after a month.
- `apps/runner/src/inbox/attention.ts` — the moment in a thread that deserves a row, built from
  the answer push already uses, so a thread that pushes also appears on the page for someone with
  notifications off. The id is the event's own (`turn_end.at`, or the approval's id).
- `apps/runner/src/push/notifier.ts` — `attention(event)` and `chatUrl(session)` extracted from
  `attentionMessage`; its output and its tests are unchanged.
- `apps/runner/src/inbox/github.ts` — the GitHub half: per project, `review-requested:@me` and
  open pull requests with failing checks become rows; rows a refresh no longer sees are forgotten.
  Throttled per workspace (60s, `?refresh=1` overrides), at most 12 projects, folders contained by
  the projects directory, and one project's failure never takes another's rows with it.
- `apps/runner/src/inbox/routes.ts` + `server.ts` + `main.ts` — `GET /inbox` (GitHub asked when
  worth asking), `GET /inbox/unread`, `POST /inbox/read` (`{ id }`, `{ path }` or nothing). A
  `path` is refused unless it is a plain console path, so a call cannot dress itself up as a page.
- `apps/console/src/modules/inbox/` — the page, its service, the store the page and the sidebar
  share, and the route-shape helper. Every machine answers, so a project on an environment keeps
  its items there; one machine down is not a failure to show.
- `apps/console/src/app.tsx` — `/inbox`.
- `apps/console/src/modules/shell/components/sidebar.tsx` — the entry, first among the pages, with
  the kit's `Count`.
- `apps/console/src/routes/app-shell.tsx` — `/inbox` scrolls inside itself, and arriving at a
  thread or a project's pull requests marks what was waiting about it read, however the person got
  there.

### Decisions worth knowing

- Only *unwatched* moments become rows — the same rule push already uses. An agent that finishes
  while someone is watching the board is not "waiting".
- Opening a thread marks every row about that thread read, not only the row tapped: the person is
  going there to deal with it, and the card asks for exactly that.
- The sidebar count is read once per sign-in and after every read. It goes stale when an item
  arrives while the app is open, which push already covers. Polling it (or pushing a count with
  the notification) is the obvious follow-up, deliberately not built here.
- GitHub is polled on open rather than pushed, because there is no webhook receiver. Raising a
  card for one is the natural follow-up; the throttle and per-project failure handling are the
  price of polling for now.
- No entry in `apps/docs/content/docs/backend-api.mdx`: that page is the contract for `apps/api`,
  and the runner's routes (including `/push/*`) are not documented there today.

### Follow-ups

- Watch the sidebar count while the app is open (poll, or carry the count in the push payload).
- A card for GitHub webhooks, so a review request does not wait for someone to open the page.
- Consider `GET /inbox` on the pulls screen's project switch, so a project's PR items do not wait
  for a visit to the Inbox.
