title: Portable Grid
description: Run the whole of Grid from one command — on a laptop, a VPS or a GitHub Codespace.
---

Grid is one disposable, reproducible bundle. The same checkout runs anywhere Bun runs, and one
command brings all of it up behind a single port:

```bash
bun install
bun run grid
```

`bun run grid` (the `apps/launcher` workspace) prepares whatever a fresh machine is missing, then
runs the API, the runner and the console together and stops them together:

1. **Data directory** — `.grid/` in the checkout (gitignored), or `GRID_DATA_DIR`. It holds the
   generated secrets, the first-run setup link, the chat database and, by default, new
   project folders.
2. **Secrets** — `JWT_SECRET` and `AUTH_TOKEN_SECRET` are generated once per data directory, so
   sign-ins survive restarts.
3. **Postgres** — `DATABASE_URL` if set; otherwise the repo's Postgres container is started with
   Docker (`docker/compose/postgres.yml`).
4. **Migrations** — applied on every start, waiting for a just-started Postgres.
5. **Setup link** — while nobody has signed up, a one-time setup link is printed and kept in
   `.grid/setup-link.txt` (mode 600); each start issues a fresh one. Whoever opens it creates the
   owner account and the first workspace. Signup then stays closed: people join by invite, unless
   the owner opens it (`PATCH /api/v1/instance`).
6. **Console** — built on first start (`GRID_REBUILD=1` rebuilds).
7. **Gateway** — the console on `GRID_PORT` (default `8080`), with `/api` and `/runner`
   (WebSocket included) forwarded behind it — the only port to expose.

Only one Grid runs per data directory; a second start reports the running one and exits.

## GitHub Codespaces

Open the repository in a Codespace. The dev container (`.devcontainer/`) comes with its own
Postgres, installs dependencies, and starts Grid in the background on attach — port **8080**,
labelled *Grid*, opens in the browser. The log is `.grid/grid.log`; the first-run setup link is
in `.grid/setup-link.txt`.

In a Codespace, projects live under `/workspaces`, next to the checked-out repositories. Install
the agent CLIs you want Grid to drive (Claude Code, Codex, opencode…) in the Codespace's terminal
and sign them in there; the runner finds them on `PATH`.

## Environments: one Grid driving another

Any Grid can pair with another machine running Grid (a Codespace, a VPS, a second laptop) and
open terminals there, through its own console. Environments are disposable; the home Grid keeps
your sign-in, projects and settings.

**How it stays secure**

- **Network.** The machines meet on your Tailscale network. The environment's runner listens only
  on its tailnet address, so WireGuard encrypts and authenticates every packet, and nothing is
  published to the internet. A home Grid only accepts tailnet addresses (`….ts.net`, `100.64/10`)
  unless `RUNNER_ENVIRONMENT_HOSTS` allows another host over https.
- **Pairing.** The environment shows a one-time code (`bun run grid:pair`, valid ten minutes, and
  ten wrong guesses void it). The home Grid trades it for a 256-bit secret; the environment keeps
  only its hash, bound to the person who paired.
- **Your sign-in never leaves home.** The console talks to its own runner under `/env/<id>/…`. The
  home runner checks your session itself, then calls the environment with the pairing token in its
  place.
- **Revocable.** Removing the environment deletes the secret on both sides.

**Pair a Codespace**: follow `.devcontainer/README.md` — a tagged, ephemeral Tailscale auth key as
the `TS_AUTH_KEY` Codespaces secret, rebuild, `bun run grid:pair`, then Settings → Environments at
home.

## Always on, on your own machine

`bun run dev` is for working on Grid: Vite and Next.js dev servers, Solid's dev checks and file
watchers, which use far more memory and are not meant to run for days. To keep a checkout's stack
running (the web app, console, docs, API and runner on their usual ports, with your own `.env`),
build once and run the production start:

```bash
bun install
bun run build
bun run start
```

`start` serves the built console (`vite preview`, with `/api` and `/runner` forwarded as in dev, and
headers that stop other sites framing it)
and the built Next.js apps, and runs the API and runner without watching files. Rebuild and
restart to pick up changes. It does not run the launcher: `bun run grid` is the one-port bundle
above, with its own data directory.

As a systemd user service, from a checkout kept for serving (for example a detached worktree of
`main`):

```ini
# ~/.config/systemd/user/grid.service
[Unit]
Description=Grid
After=network-online.target

[Service]
WorkingDirectory=%h/Projects/grid-serve
ExecStart=%h/.bun/bin/bun run start
Restart=on-failure
RestartSec=10
KillMode=control-group
UMask=0077

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now grid.service
loginctl enable-linger "$USER"   # keep it running while you are logged out
```

To update, use **Settings → Machines → Grid version → Update** (owners and admins). It runs
`scripts/bash/update-grid.sh`, which builds the latest `main` in a release of its own while the
running version keeps serving, then switches over and restarts the units in `GRID_UPDATE_UNITS`
(default `grid-dev.service grid-pwa.service`). A failed install or build changes nothing that is
running. The first update turns the serving checkout into this layout:

- `serve`: a link to the release in use; point the units' `WorkingDirectory` here.
- `releases/`: one checkout per version; the one in use and the one before it are kept, so switching
  back is relinking `serve` and restarting.
- `shared/`: the API's `.env`, its uploads and the launcher's data, linked into every release.

By hand, the same: `bash serve/scripts/bash/update-grid.sh`.

`UMask=0077` keeps the logs and data the service writes
readable by you alone.

## A VPS

With Docker on the server:

```bash
docker compose -f docker/compose/postgres.yml -f docker/compose/grid.yml up -d --build
docker compose -f docker/compose/postgres.yml -f docker/compose/grid.yml exec grid cat /data/setup-link.txt
```

The `grid` image (`docker/grid.Dockerfile`) keeps its data in the `/data` volume and projects in
`/projects`. Put HTTPS in front of port 8080 (Caddy, a Cloudflare tunnel, Tailscale) and set
`GRID_ALLOWED_HOSTS` to the domain people open it on.
Grid's gateway already tells browsers no other site may frame the console; a server that serves
the built console's files itself should send `Content-Security-Policy: frame-ancestors 'self'` too.

Without Docker, install Bun and Postgres, set `DATABASE_URL`, and run `bun run grid` under your
process manager of choice.

## Settings

| Variable | Default | Purpose |
|----------|---------|---------|
| `GRID_PORT` | `8080` | The one public port |
| `GRID_DATA_DIR` | `<repo>/.grid` | Secrets, setup link, chat database |
| `GRID_PROJECTS_DIR` | `<data>/projects`, `/workspaces` in a Codespace | Where project folders go |
| `DATABASE_URL` | Docker Postgres on `:5433` | Postgres connection |
| `GRID_ALLOWED_HOSTS` | — | Extra hostnames for the gateway (Tailscale and Codespaces are built in) |
| `GRID_PUBLIC_URL` | — | The address printed at start |
| `GRID_API_PORT` / `GRID_RUNNER_PORT` | `4000` / `4100` | Internal loopback ports |
| `GRID_PAIRING` | on when `TS_AUTH_KEY` is set | Let a home Grid pair with this one over the tailnet |
| `RUNNER_ENVIRONMENT_HOSTS` | — | Non-tailnet hosts a home Grid may add as environments (https only) |
