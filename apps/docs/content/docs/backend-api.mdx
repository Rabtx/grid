This page is the one place the Grid API contract lives (`apps/api`, Hono on Bun). The agent contract in
`.agents/agent-contract.md` points every role here: consumers read it before using an
endpoint, and backend updates it in the same commit as any public API change.

Base URL prefix: `/api/v1` (URI versioning). Auth uses JWT bearer tokens unless noted.

## What belongs here

- Every public endpoint: method, path, auth requirement, request and response shape.
- The response envelope, error shape and status-code conventions.
- Pagination, filtering and sorting conventions.
- Breaking changes, with a dated changelog entry below.

## What does not

- Implementation detail, internal service structure, database schema.
- Anything still being designed — raise a board card for that instead.

## Endpoints

Auth, profile and billing routes also live under `/api/v1/*`; the contract suite in
`apps/api/test/contract` pins their responses.

### Workspaces

A workspace is the company: it owns projects and billing. Every route takes a bearer token;
`:ws` is the workspace slug. A workspace you do not belong to answers `404`, like one that does
not exist. Roles: **owner** (billing, slug, deleting), **admin** (settings, members), **member**
(the work). A workspace always keeps at least one owner.

| Method | Path | Role | Purpose |
| --- | --- | --- | --- |
| `GET` | `/api/v1/workspaces` | — | Your workspaces, each with your `role` |
| `POST` | `/api/v1/workspaces` | — | Create one; you become its owner (`201`) |
| `GET` | `/api/v1/workspaces/:ws` | member | Get one |
| `PATCH` | `/api/v1/workspaces/:ws` | admin (owner for `slug`) | Update name, icon, colour or slug |
| `DELETE` | `/api/v1/workspaces/:ws` | owner | Delete it with all its projects (`204`) |
| `GET` | `/api/v1/workspaces/:ws/members` | member | List members |
| `PATCH` | `/api/v1/workspaces/:ws/members/:userId` | admin (owner for owners) | Change a role |
| `DELETE` | `/api/v1/workspaces/:ws/members/:userId` | admin, or yourself | Remove a member or leave (`204`) |

### Projects, tasks and notes

Under `/api/v1/workspaces/:ws/projects`; the bare `/api/v1/projects` means your default
workspace (the oldest you own, made on first use if you have none). `:slug` is the project slug;
`:number` is the task number on that board.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `…/projects` | List the workspace's projects |
| `POST` | `…/projects` | Create a project (`201`) |
| `GET` | `…/projects/:slug` | Get one project |
| `PATCH` | `…/projects/:slug` | Update a project |
| `GET` | `…/projects/:slug/tasks` | List tasks on a project board |
| `POST` | `…/projects/:slug/tasks` | Create a task (`201`) |
| `PATCH` | `…/projects/:slug/tasks/:number` | Update a task (including stage moves) |
| `DELETE` | `…/projects/:slug/tasks/:number` | Delete a task (`204`) |
| `GET` | `…/projects/:slug/notes` | List notes, newest first |
| `POST` | `…/projects/:slug/notes` | Create a note (`201`) |
| `PATCH` | `…/projects/:slug/notes/:id` | Edit a note |
| `DELETE` | `…/projects/:slug/notes/:id` | Delete a note (`204`) |

`POST /api/v1/auth/logout` accepts an optional bearer access token. A verified
JWT revokes only its own user/session pair even if another tab rotated the refresh
cookie. Without a valid JWT, logout retains its current-refresh-cookie (or native
refresh-token body) proof requirement. The browser cookie is cleared idempotently.

OTP and MFA login challenges enforce their attempt limit atomically: concurrent
incorrect codes each count, and reaching the limit permanently consumes that
challenge. Further submissions require a new challenge.

### Setup, signup and invites

A new Grid has no accounts. While nobody has signed up, the launcher (or the API container's
entrypoint) prints a one-time setup link, `/setup?code=…`; the setup call creates the owner (email
already verified) and the first workspace, and signs them in. Signup is then **closed**:
`POST /auth/register` needs an `inviteToken`, unless this Grid's owner opens signup. Google
sign-in makes new accounts only while signup is open.

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/api/v1/instance` | none | `{ setupNeeded, signupOpen }` |
| `PATCH` | `/api/v1/instance` | Grid owner | Open or close signup (`{ signupOpen }`) |
| `POST` | `/api/v1/instance/setup` | setup code | First run: owner account and workspace, signed in (`201`); `409` once set up |
| `GET` | `/api/v1/workspaces/:ws/invites` | admin | Pending invites |
| `POST` | `/api/v1/workspaces/:ws/invites` | admin | Invite by email (sent) or as a link (`{ email?, role }`); the reply carries the `token` and `url` once (`201`) |
| `DELETE` | `/api/v1/workspaces/:ws/invites/:id` | admin | Revoke (`204`) |
| `GET` | `/api/v1/invites/:token` | none | What the invite is for: workspace, role, email |
| `POST` | `/api/v1/invites/:token/accept` | JWT | Join with the invite's role |

Invites last 7 days and work once. One for an email only works for that address, and signing up
with it starts the account verified. Roles are `admin` or `member`; ownership is handed over, not
invited.

### Billing

Plans belong to a workspace. `GET /api/v1/billing/subscription?workspace=:ws` shows it to any
member; `POST /api/v1/billing/checkout` and `/portal` take an optional `workspace` in the body and
need its owner. Without one they use your default workspace.

### Runner automations

Automations belong to the project's machine and use the runner URL prefix `/runner` (not
`/api/v1`). These routes require the same bearer token as runner chat routes. Send
`X-Grid-Workspace: <workspace-slug>` to select a workspace; otherwise the token's default
workspace is used. Responses wrap values in `{ "data": ... }`; errors use `{ "message": ... }`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/runner/automations` | List up to 200 jobs in the workspace, each with `lastRun` |
| `POST` | `/runner/automations` | Create a job (`201`) |
| `GET` | `/runner/automations/templates` | Six static form templates; does not create a job |
| `GET` | `/runner/automations/:id` | Read a job |
| `PUT` | `/runner/automations/:id` | Replace a job (owner only) |
| `DELETE` | `/runner/automations/:id` | Delete an idle job (`204`, owner only) |
| `POST` | `/runner/automations/:id/toggle` | Flip enabled state (owner only) |
| `POST` | `/runner/automations/:id/run` | Start a run now (`202`, owner only) |
| `GET` | `/runner/automations/:id/runs` | Latest 50 runs, newest first |
| `GET` | `/runner/automations/:id/webhook` | Its webhook's `{ path, secret }` (owner only; the secret is made on first read) |
| `POST` | `/runner/automations/:id/webhook/rotate` | A new secret; the old one stops working at once (owner only) |
| `POST` | `/runner/hooks/automations/:id` | A webhook delivery, with no sign-in (below) |

Create and replace take the complete form: `{ name, prompt, provider, model, effort, mode,
project, workspaceMode, enabled, triggers }`. `model`, `effort`, and `mode` may be `null`.
`workspaceMode` is `folder` or `worktree`. `project` must have a linked folder on this machine.
`triggers` contains one to five schedule or GitHub event triggers. A schedule has `kind:
"schedule"`, `cadence` (`hourly`, `daily`, `weekdays`, `weekly`), an IANA `timezone`, and
`minute` for hourly, `time` (`HH:MM`) for daily or weekdays, or `day` (0–6, Sunday first) plus
`time` for weekly. An event has `kind: "event"` and `event` (`pull_opened`,
`review_requested`, `checks_failed`); GitHub must be connected. The returned job includes its
`id`, owner and workspace, timestamps, and `nextRunAt`. A run includes its trigger, status,
timestamps, error, and `sessionId`; that ID opens an ordinary chat transcript.

A webhook trigger is `{ kind: "webhook", filter?, template? }`: `filter` is `{ path, equals }`
(a dotted path into the JSON sent, run only when its value is `equals`) and `template` is what
the agent is told, with each `{{path}}` filled in (the whole payload, cut to 12,000 characters,
when there is none). A delivery proves itself with the automation's secret: an HMAC-SHA256 of the
raw body as `X-Grid-Signature` or `X-Hub-Signature-256` (`sha256=<hex>`), or `?token=<secret>` for
a service that cannot sign. It answers `401` unproved (and for an automation without a webhook),
`409` when the automation is off, `413` over 256 KiB, `429` past 30 a minute, `202` "filtered out"
or "running" (`{ run, status }`), and `200` for a delivery already run: each is run once, by
`X-GitHub-Delivery`, `X-Request-Id`, `Idempotency-Key`, `X-Delivery-Id` or `X-Webhook-Id`, else by
the body's hash. The run's trigger is `webhook`, and its first message says what was sent comes
from outside Grid, as data and not instructions. From outside the machine the address is the
console's `/runner/hooks/automations/:id`.

Unknown IDs return `404`; invalid fields and disconnected GitHub triggers return `400`.
Nonowners receive `403` for changes and run-now. Active job deletion and the 200-job limit
return `409`; unsupported methods return `405`. Request bodies over 32 KiB return `413`.

### Runner skills

Skills are kept on the runner and use the runner prefix `/runner` with bearer authentication and
`X-Grid-Workspace` selection. `GET /runner/skills` returns the workspace's skills, linked project
slugs and registered agent providers. Each provider reports `delivery: "message-context"` because
Grid includes applicable enabled skills with each chat message.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/runner/skills` | List skills, linked projects and agent delivery support |
| `POST` | `/runner/skills` | Write a skill from `{ skillMarkdown, scope, source }` (`201`) |
| `POST` | `/runner/skills/import/git` | Import one skill from a public HTTPS GitHub repository archive (`201`) |
| `POST` | `/runner/skills/import/upload` | Import a folder's multipart files or one ZIP archive (`201`) |
| `PATCH` | `/runner/skills/:id` | Enable, disable, edit `SKILL.md`, or change scope |
| `DELETE` | `/runner/skills/:id` | Remove a skill (`204`) |

`scope` is `{ "type": "workspace" }` or `{ "type": "project", "project": "<slug>" }`; a project
must have a linked folder on this runner. A project skill with the same name overrides the workspace
skill for that project. `SKILL.md` requires kebab-case `name` and a `description` in its YAML
frontmatter. A skill may contain up to 20 additional text files and 64 KiB total. The archive importer
reads ZIP entries without extracting or running repository files. Git imports accept public GitHub
repository URLs; archives are limited to 8 MiB. Changes require the workspace's `integrations`
permission. Invalid input returns `400`, oversized content `413`, duplicate name/scope pairs `409`,
unknown or foreign skills `404`, and forbidden writes `403`.

### Runner attention and activity

These routes use the runner prefix `/runner`, bearer authentication and
`X-Grid-Workspace` selection, including `/runner/env/:id` for paired machines.
Only the selected workspace's threads are returned. Values use `{ data: ... }`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/runner/chat/waiting` | Unresolved approvals in running threads |
| `POST` | `/runner/chat/sessions/:id/approve` | Answer a pending approval with `{ approvalId, optionId }` |
| `GET` | `/runner/chat/activity?project=:slug` | Latest turn per active or question thread, plus 40 recent idle threads in the project |
| `POST` | `/runner/chat/sessions/:id/cancel` | Ask a running agent to stop (`204`) |

A waiting item includes `sessionId`, `project`, `thread`, `provider` and an `approval`
with `id`, `title`, nullable `detail`, and `options` (`id`, `label`, `kind`). Approving
requires the `approveCommands` role permission. The approval must belong to the
specified thread, remain pending and offer the chosen option; `null` declines.
Invalid input/options return `400`, missing/foreign threads `404`, stale requests
`409`, forbidden roles `403`, and delivery failures `502`. Successful delivery is `204`.

Activity includes `id`, `project`, `title`, `provider`, `running`, `waiting`, nullable
`startedAt`, `endedAt`, `result` (`done`, `cancelled`, `error`), latest tool title,
and optional step counts (`done`, `total`). This is a bounded recent-thread view,
not all-time run analytics; the Console labels its metrics accordingly. No transcript
messages, reasoning or file contents are returned. Stop requires `startAgents`,
answers `409` for an ended agent and uses the same `404` workspace boundary.

### Runner agent turns: queue, steering, questions, subagents, visuals, checkpoints and forks

Same prefix, authentication and workspace selection as above.

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `POST` | `/runner/chat/sessions/:id/fork` | `startAgents` | New thread from `{ at?, worktree? }` (`201`, the thread) |
| `POST` | `/runner/chat/sessions/:id/checkpoints/:turn/restore` | `startAgents` | Undo a turn: its files back to how it found them (`204`) |

A fork copies the source's log up to the end of the turn of user message `at` (a user event's
`id`; the whole settled log when left out), then appends `{ type: "forked", from: { id, title } }`.
It works in the source's folder, or in a new worktree with `worktree: true`, and its agent starts
fresh with the earlier conversation in its first message. Forking from a message that is not in
the thread answers `404`; from a turn still running, `409`.

Undo restores the files the turn and every later turn changed to the turn's start checkpoint,
saving the current tree under `refs/grid/checkpoints/<thread>/<turn>/undo` first. It answers `409`
while the thread's agent, or another running thread in the same repository, is working, or when
the folder is not in git; `404` when the checkpoint is gone.

The chat socket takes these commands after `hello`, besides `prompt`, `cancel`, `approve` and
`configure`:

| Command | Purpose |
| --- | --- |
| `{ t: "prompt", text, attachments?, delivery? }` | While the agent works, the message waits in the thread's queue; `delivery: "steer"` sends it into the turn going on |
| `{ t: "queue", action, id? }` | `remove`, `steer` (send one now), `clear`, `pause` or `resume` the queue |
| `{ t: "answer", id, answers }` | Answer a `question` event: `{ [questionId]: string[] }`, or `null` to dismiss |

New events in the log: `steer` (`text`, `attachments?`); `question` (`id`, `questions` with
`id`, `header`, `question`, `options`, `multiSelect?`) and `question_answered` (`id`, `answers`
or `null`); `subagent` (upserted by `id`: `title`, `agent`, `status` `running` / `completed` /
`failed` / `cancelled`, `prompt`, `result`, `activity`, `at`, `endedAt`), with a subagent's own
`tool` events carrying `parent`; `visual` (`id`, `title`, `format` `components` or `html`,
`blocks` or `html`, `height`); `checkpoint` and `checkpoint_restored` (`turn`, `files` of
`path`, `added`, `removed`); and `forked`. `user` events now carry an `id`. The queue is not in
the log: `{ type: "queue", items, paused }` is sent on attach and whenever it changes, and is
kept with the thread so a restarted runner still has it, held.

Agents publish visuals through Grid's own MCP server (`grid`, tool `show_visual`), started per
thread. It calls `POST /chat/tools/visual` on the runner with the key the runner started it with;
the runner checks the spec (16 blocks, 64 KB of blocks or 256 KB of HTML, six per turn) and
records it only while that thread's turn is running.

### Runner handoffs, side chats and crews

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `POST` | `/runner/chat/sessions/:id/handoff` | `startAgents` | Hand the thread to `{ provider, model?, mode?, effort?, newThread? }` (`200`, or `201` with `newThread`) |
| `GET` | `/runner/chat/sessions/:id/sides` | member | The thread's side chats |
| `POST` | `/runner/chat/sessions/:id/sides` | `startAgents` | Open a side chat, `{ provider?, model? }` (`201`) |
| `GET` | `/runner/chat/crews?project=:slug` | member | A project's crews, each with its `workers` |
| `POST` | `/runner/chat/crews` | `startAgents` | Start a crew: `{ project, name, provider, model?, instructions?, workerProvider?, workerModel?, parallel?, cwd? }` (`201`, `{ crew, session }`) |
| `GET` | `/runner/chat/crews/:id` | member | A crew by its id or its coordinator thread's id; `null` when none |
| `PATCH` | `/runner/chat/crews/:id` | `startAgents` | Change `name`, `instructions`, `parallel` (1–8), `paused`, `workerProvider`, `workerModel` |
| `POST` | `/runner/chat/crews/:id/workers/:worker/retry` | `startAgents` | Give a member another go (`204`) |
| `POST` | `/runner/chat/crews/:id/workers/:worker/stop` | `startAgents` | Stop a member (`204`) |

A same-thread handoff is refused while the agent works (`409`), to the agent it already has
(`400`) or to one not installed (`400`). It parks the old agent, records
`{ type: "handoff", from: { provider, model }, to: { provider, model } }`, and the new agent's
first message carries the conversation so far. With `newThread` it is a fork (see above) with the
new agent. A side chat is a fork with `parentId` set: it is left out of the project's thread list,
cannot have side chats of its own, and is deleted with its thread.

A crew's coordinator is a thread started with a crew role whose brief is the crew's instructions.
Only that thread's agent is offered the crew tools (`crew_start_worker`, `crew_message_worker`,
`crew_list_workers`, `crew_stop_worker`). Members are threads of their own (in a worktree unless
the folder is not in git); at most `parallel` work at once and the rest are `queued`. A worker's
`state` is `queued`, `working`, `done`, `failed`, `stopped` or `needs_you`, with `running` and
`waiting` (its turn waits on a person) alongside. Turn ends are reported to the coordinator as a
`[Crew report]` message. A running member quiet for 10 minutes is nudged in its turn; quiet 5
more, its turn is restarted once; quiet again, it is stopped and marked `needs_you`. Members
waiting on a person are never nudged, and a runner restart marks members that were working as
`needs_you` unless Grid carried their turn on (see below).

### Runner-key board routes (API)

Grid's board tools for agents (`board_list_tasks`, `board_create_task`, `board_update_task`) go
through the API with `Authorization: Runner <key>`, acting as the thread's owner:

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/runner/tasks/:workspaceId/:slug?user=:userId` | The project's tasks |
| `POST` | `/api/v1/runner/tasks/:workspaceId/:slug` | `{ user, task }`: create, with the board's own fields |
| `PATCH` | `/api/v1/runner/tasks/:workspaceId/:slug/:number` | `{ user, task }`: update |

The person's own access applies: a project they cannot see is `404`, and invalid fields `400`.
Grid's tools are listed per thread at `GET /chat/tools?thread=` and called at
`POST /chat/tools/call` (`{ thread, name, args }` → `{ data: { text, image? } }`, `image` being
`{ data, mimeType }` for a tool that answers with a picture), both proved with the key the runner
started `grid-tools.ts` with and needing no person's sign-in.

### Runner accounts, usage and the browser

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/chat/accounts` | member | `{ supported, accounts, usage }`: the agents that can run as another account here, your accounts, and what each (`account: null` is the machine's own sign-in) has used |
| `POST` | `/runner/chat/accounts` | member | Add an account: `{ provider, label }` (`201`); `400` for an agent without accounts, `409` past 8 per agent |
| `PATCH` | `/runner/chat/accounts/:id` | member | Rename: `{ label }` |
| `DELETE` | `/runner/chat/accounts/:id` | member | Remove it and its config folder (`204`) |
| `POST` | `/runner/chat/accounts/:id/sign-in` | terminals | A terminal running the agent's own sign-in for that account (`201`, the terminal) |
| `GET` | `/runner/chat/browser/:thread` | member | The thread's page: `{ available, open, url, title, version }` |
| `GET` | `/runner/chat/browser/:thread/frame` | member | A JPEG of the page as it is now (`404` when none is open) |
| `POST` | `/runner/chat/browser/:thread/open` | `startAgents` | Open `{ url }` (http, https; `localhost:3000` is taken as http) |
| `POST` | `/runner/chat/browser/:thread/back` · `/reload` | `startAgents` | Go back, reload |
| `POST` | `/runner/chat/browser/:thread/click` | `startAgents` | Click `{ x, y }` in page pixels (1280×800) |
| `POST` | `/runner/chat/browser/:thread/type` · `/key` · `/scroll` | `startAgents` | Type `{ text }`, press `{ key }`, scroll `{ by }` pixels |
| `POST` | `/runner/chat/browser/:thread/close` | `startAgents` | Close the page and its cookies (`204`) |

An account is a config folder of its own (`CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for
Codex) under the runner's data folder; `POST /runner/chat/sessions` takes `account` to run a thread
as one (`400` when it is not yours for that agent), and threads report it as `account`. Usage comes
from what the agents report as they work (Claude Code's `rate_limit_event`, Codex's
`account/rateLimits/updated` and `account/rateLimits/read`): each `limits` entry is
`{ window, usedPercent, resetsAt, limited }`, and a window past its reset reads `0`.
`GET /runner/chat/running` entries carry `waiting` (the turn waits on a person).

The browser is one headless Chromium on the runner's machine (`GRID_BROWSER` points at one when
it is not in the usual places; `available: false` when there is none; `GRID_BROWSER_NO_SANDBOX=1`
runs it without Chromium's sandbox on a machine that cannot give it one), started on the first page
and stopped ten minutes after the last closes; each thread's page is its own browser context.
Agents drive it with Grid's tools `browser_open`, `browser_snapshot`, `browser_click`,
`browser_type`, `browser_press`, `browser_scroll`, `browser_back` and `browser_screenshot` (which
answers with the picture); each answers with the page's numbered elements and text. Opening or
moving to another address records `{ type: "browser", url, title }`, which opens the browser pane
beside the thread. A thread's page closes with the thread.

### Runner orchestration: steering, restarts, retries, forks and thread tools

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `POST` | `/runner/chat/sessions/:id/merge` | `startAgents` | Bring a fork's finished work back into the thread it was forked from (`200`, `{ into, turns }`) |

**Agent capabilities.** `GET /runner/chat/providers` entries carry
`capabilities: { steer: "native" | "restart", resume, fork }` (left out: `restart`, `false`,
`false`). Claude Code and Codex steer, resume and fork natively; ACP agents resume when they can
load a session.

**Steering an agent that cannot take a message mid-turn** stops its turn and starts the next with
the message, which is logged as `user` with `steered: true` and is told it was stopped for it.
The stopped turn ends with `{ type: "turn_end", reason: "cancelled", restarted: true }`. A stop
that has not taken effect after 30 seconds ends the agent's process; the turn ends as `cancelled`
and the next message resumes the conversation in a new process.

**Safe retries.** `{ t: "prompt", …, requestId }` on the chat socket names a send (up to 100
letters, digits, `-`, `_`): the same id again in that thread is taken as already sent and does
nothing. Receipts are kept a week. The console sends a request id with every message and sends
recent ones again after a reconnect.

**Restarts.** The turn an agent is working on is kept with its thread until it ends. When the
runner starts, each thread cut off mid-turn has that turn closed (approvals and questions it was
waiting on are voided) and is carried on: its turn ends `{ reason: "cancelled", continued: true }`
and Grid sends `CONTINUE_PROMPT` as a `user` event with `origin: { kind: "grid", reason:
"restart" }`, resuming the agent's own conversation; its queue goes on after. A turn that was
waiting on the person, whose agent is not installed, or that was carried on three times within
five minutes is closed as an `error` instead and left for the person. `GRID_CONTINUE_TURNS=0`
turns carrying on off. A runner stopped with SIGINT or SIGTERM leaves its turns to be carried on.

**Forks and handoffs.** A fork of a whole settled thread, with the same agent, by an agent with
`fork`, branches the agent's own conversation (`claude --resume … --fork-session`, Codex
`thread/fork`): the fork's agent remembers everything, not only the transcript. Otherwise, and if
branching fails, the fork's agent is told the thread. A handoff keeps the leaving agent's session;
handing the thread back to it (within 20 turns) resumes that session, records `handoff` with
`resumes: { turns }`, and tells it only the turns it missed. An agent that turns out not to have
the session it was asked to resume starts a new one and is told the thread, once.

What an agent is told of a thread it does not remember is a budgeted selection of the real
conversation, not a summary: the first request, then the newest turns, each with the reply, files
changed, commands run (and which failed), and whether it was stopped or failed. Turns left out are
named, to read with `thread_read`.

**Merge-back** sends what a fork did since it branched (or since it was last brought back) to the
source thread as its next message, `origin: { kind: "merge", thread: { id, title } }`, queued
while its agent works, and records `{ type: "merged", into: { id, title }, turns }` in the fork.
It answers `400` for a thread that is not a fork, `404` when the source is gone, and `409` when
nothing new has finished.

**Thread tools.** Every thread's agent gets Grid's thread tools: `thread_list`, `thread_read`
(turns from `from`, with any question waiting), `thread_start` (`prompt`, `title?`, `provider?`,
`model?`, `mode?`, `worktree?`, `wait?`, `timeout?`, `requestId?`), `thread_send` (`delivery`
`auto`, `queue` or `steer`), `thread_wait` (up to 100 seconds), `thread_stop` and `thread_answer`
(answer a thread's question). A thread acts as its person: it reads any thread of the workspace
but changes only its person's, starts threads only when they may start agents, and never gives a
thread a broader permission mode than its own (`403`). Threads started from threads go three deep
at most, and one turn starts ten at most. A thread started this way carries `delegatedBy` and gets
only its prompt, as `user` with `origin: { kind: "agent", thread: { id, title } }`. Unless the
starting thread was waiting on it, Grid tells the starting thread when it finishes, fails or is
stopped, and when it asks a question, as a `user` message with
`origin: { kind: "grid", reason: "report" }`. Crew members' questions go to their coordinator the
same way.

### Runner autonomy: usage limits, pull request watches, goals and idle compaction

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/chat/sessions/:id/goal` | member | The thread's goal, or `null` |
| `POST` | `/runner/chat/sessions/:id/goal` | `startAgents` | Set one, `{ objective, maxTurns? }` (`201`; 20 turns by default, 100 at most), or `{ action: "pause" \| "resume" \| "clear" }` |
| `DELETE` | `/runner/chat/sessions/:id/limit-wait` | `startAgents` | Don't carry the thread on when its usage limit resets (`204`; `404` when it is not waiting) |

`PUT /runner/chat/projects/:slug/settings` now takes either or both of `worktrees` and
`idleCompact`; those left out keep their value.

**Usage limits.** A turn that fails because the person's plan is used up ends with an error the
console reads as "usage limit" (`retryable: false`). When its reset time is known (from the agent's
words: Claude's `…|<unix seconds>`, "try again at …", "resets 3pm (Zone)"; or from what the
account's agents last reported as `limited` with a `resetsAt`), Grid logs
`{ type: "limit_wait", resetsAt }` and carries the thread on a minute after the reset with a
`user` message, `origin: { kind: "grid", reason: "limit" }`, then logs the wait as
`ended: "resumed"`. A message from the person first, or the `DELETE` above, ends it as
`"cancelled"`. The wait is kept across restarts; resets more than eight days off are not waited
for, nor is the same reset twice. `GRID_LIMIT_RESUME=0` turns it off.

**Pull request watches.** Every thread's agent has `watch_pull_request` (`number`, `repo?` as
`owner/name`, by default the GitHub remote of the thread's folder) and `unwatch_pull_request`
(`number?`; none stops them all). Grid reads each watched pull request every two minutes through
GitHub's REST API (`gh api`), once for all threads watching it, and wakes each thread with a
`user` message, `origin: { kind: "grid", reason: "pull" }`, when a check on the head fails, every
check has passed, the branch starts to conflict, or someone other than the signed-in GitHub user
reviews or comments. A watch ends when the pull request is merged or closed, when the person
stops the thread, after ten wakes in a row with only comments, or after eight failed reads in a
row; a rate limit only pauses it.

**Goals.** `/goal <what done means>` in the composer (or the route above) sets the thread's goal
and logs `{ type: "goal", objective, status, turns, maxTurns, note? }` each time it changes;
`status` is `active`, `paused`, `met`, `blocked` or `cleared`. Grid sends the agent a turn for the
goal (`origin: { kind: "grid", reason: "goal" }`) each time a turn ends, behind anything queued,
until the agent's reply begins with `GOAL MET` (and how it checked) or `GOAL BLOCKED` (and what it
needs), or the goal's turns run out (paused; resuming gives as many again). The person's Stop
pauses it; a failed turn leaves it for the next turn to end.

**Idle compaction** (project setting `idleCompact`, off by default): a Claude Code thread whose
conversation is 60,000 tokens or more and goes quiet is sent `/compact`
(`origin: { kind: "grid", reason: "compact" }`) 90 seconds before Claude's prompt cache for it
expires: an hour after its last turn on a plan, five minutes with `ANTHROPIC_API_KEY`. Anything
happening in the thread first cancels it; timers do not survive a restart. Claude Code `usage`
events now carry `contextUsed`, the input its latest request read.

### Runner outside agents, guests, search and snooze

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/chat/agent-keys` | member | Your agent keys (never their tokens), each with `spentUsd`: what its threads cost in 30 days |
| `POST` | `/runner/chat/agent-keys` | `startAgents` | Make one, `{ name, write?, mode?, project?, provider?, expiresInDays?, projects?, budgetUsd?, ownThreads? }` (`201`, `{ key, token }`; the token is shown only now; 20 a person) |
| `DELETE` | `/runner/chat/agent-keys/:id` | member | Revoke one of yours (`204`) |
| `POST` | `/runner/mcp` | agent key | Grid's MCP endpoint (below) |
| `GET` | `/runner/chat/sessions/:id/guest-links` | member | The thread's live guest links |
| `POST` | `/runner/chat/sessions/:id/guest-links` | member | Share it, `201`, `{ link, token }` (a day; 5 a thread) |
| `DELETE` | `/runner/chat/sessions/:id/guest-links(/:linkId)?` | member | Stop one link, or every link to the thread (`204`) |
| `POST` | `/runner/chat/sessions/:id/guest-requests/:requestId` | `startAgents` | `{ action: "send" \| "dismiss" }` a guest's question (`204`; `409` once handled) |
| `GET` | `/runner/guest/:token?after=` | the link | What a guest sees, no sign-in |
| `POST` | `/runner/guest/:token/messages` | the link | A guest asks, `{ name?, text }` (`201`) |
| `PUT` | `/runner/chat/sessions/:id/snooze` | member | `{ until }` (ISO, up to 90 days) or `{ until: null }` to wake |
| `GET` | `/runner/chat/sessions/:id` | member | One thread by id (what a `grid-thread://` link names) |

**Outside agents.** `POST /runner/mcp` speaks MCP's Streamable HTTP with JSON answers
(`initialize`, `ping`, `tools/list`, `tools/call`; protocol versions `2025-06-18`, `2025-03-26` and
`2024-11-05`), for `Authorization: Bearer grid_ak_…`; anything else is `401` with
`WWW-Authenticate`. The tools are `list_projects` and Grid's thread tools (`thread_list`,
`thread_read`, `thread_wait`, and for a key with `write`, `thread_start`, `thread_send`,
`thread_stop` and `thread_answer`), acting as the key's person with at most the key's `mode`.
`thread_start` needs a project (the key's or its argument) and an agent (`provider`, the key's or
its argument), and starts at most a few threads a minute; `requestId` makes a retry safe. What an
outside agent sends is a `user` message with `origin: { kind: "outside", agent }`, the key's name.

**Guests.** A guest link's token (`grid_gl_…`) is kept only as a hash. Its view has the thread's
`title`, `running`, `expiresAt`, `next` (pass as `after` for what is new) and `events`, each with
its number `n`: `user` (`text`; `guest` for a guest's own; `from` for one the person did not type),
`message`, `tool` (`id`, `title`, `status` only), `turn_start`, `turn_end`, `guest_request` and
`guest_request_resolved`. A guest's question is logged as
`{ type: "guest_request", id, name, text }` and waits for the person; sent on, it is a `user`
message with `origin: { kind: "guest", name }` and `guest_request_resolved` with
`action: "sent"`, or `"dismissed"`. A link takes 6 questions a minute, 5 waiting at once, 4,000
characters each. Ended, stopped and unknown links all answer `404`.

**Search** (`GET /runner/search`, Ask Grid) is full-text over threads' titles and messages:
words match by prefix, accents are folded, and the best match comes first with its passage.

**Snooze.** A snoozed thread's finished turns do not notify or reach the Inbox until it wakes;
an approval, a question or a failed turn wakes it at once. Threads carry `snoozedUntil`.

**Thread links.** Grid's thread tools name threads as `[Title](grid-thread://<id>)`, and take
such a link wherever they take a thread id; the console opens it at `/thread/<id>`.

**Replay tests.** With `GRID_AGENT_RECORD_DIR` set, the runner records every agent process it
starts (what it sent and what came back, as NDJSON) for `replaySpawn` in `agents/replay.ts`.

**Scoped keys.** A key may expire (`expiresInDays`, 1–365; an expired key answers `401` like a
revoked one), work only in some projects (`projects`; its other threads are not found, and
starting work elsewhere is `403`), see and act on only the threads it started (`ownThreads`), and
have a budget of its own (`budgetUsd` per 30 days; once its threads have cost that, starting or
sending work is refused with an error that says so). Keys carry `expiresAt`, `projects`,
`budgetUsd` and `ownThreads`.

### Runner spending, budgets and the audit log

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/spend` | member | `{ today, month, byProject, byPerson, budgets, canManage }`: spent today and this month (UTC), this month by project and by person, and each budget with `spentUsd`, `since` and `state` (`ok`, `warning`, `reached`) |
| `POST` | `/runner/spend/budgets` | owner, admin | A budget, `{ scope, target?, period, limitUsd }` (`201`); `scope` is `workspace`, `person`, `project` or `automation` (with its id or name as `target`); `period` is `day` or `month` |
| `PUT` | `/runner/spend/budgets/:id` | owner, admin | Change one (its notices may come again) |
| `DELETE` | `/runner/spend/budgets/:id` | owner, admin | Remove one (`204`) |
| `GET` | `/runner/audit?before=&kind=&actor=` | owner, admin | The audit log, newest first, 100 at a time: `{ id, at, actor: { kind, id, name }, action, project, sessionId, target, detail, costUsd }` |

**Spending** is what agents report as they work: each rise in a thread's `usage.costUsd` (a
running total per agent process, starting again with a new one) is kept against its workspace,
person, project, automation run and the key that started it. Days and months are UTC.

**Budgets.** The first time in a period a budget passes 80%, and when it is reached, Grid adds an
Inbox item of kind `budget` and notifies whoever set it (and the person, for a person's budget).
When one is reached, the turns going on that it covers are stopped, and any turn it covers is
refused until the period starts again or it is raised: sending answers `402` with the reason, a
message already queued stays queued (held, with an `error` event saying why), and a thread
carried on after a restart is not.

**Audit log.** Entries have an `actor.kind` (`person`, `agent_key`, `guest`, `webhook`,
`automation`, `grid`, `agent`) and an `action`: `thread.start`, `thread.send`, `thread.stop` and
`thread.answer` by agent keys; `key.create` and `key.revoke`; `guest_link.create`,
`guest_link.stop`, `guest.ask`, `guest.send` and `guest.dismiss`; `automation.run`; and
`webhook.refused` (at most one a minute per automation); `budget.warning`, `budget.reached`, and
`thread.stop` by a reached budget; `memory.save` by a thread's agent, `memory.edit` and
`memory.remove` by a person; `review.posted` and `review.failed`. A person is named by their id;
the console shows their name. Kept 90 days.

### Runner project memory, pull request reviews and sandboxes

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/memory?project=&q=` | member, viewer | A project's memory, newest first, or what is about `q`, best first: `{ id, project, kind, text, by: { kind, id, name }, sessionId, createdAt, updatedAt, used, usedAt }` |
| `POST` | `/runner/memory` | member | Keep one, `{ project, kind, text }` (`201`; `200` with the one already there when the same text is) |
| `PUT` | `/runner/memory/:id` | member | Change its `kind` or `text` |
| `DELETE` | `/runner/memory/:id` | whoever kept it, owner, admin | Remove one (`204`) |
| `GET` | `/runner/reviews?project=` | member, viewer | `{ settings, reviews, canManage }`: how the project's review agent is set (`enabled`, `provider`, `model`, `instructions`, `ownerId`, `since`) and its latest reviews (`repo`, `number`, `title`, `head`, `status`: `running`, `posted` or `failed`, `sessionId`, `commentUrl`, `error`, `manual`) |
| `PUT` | `/runner/reviews/settings` | owner, admin | `{ project, enabled?, provider?, model?, instructions? }` |
| `POST` | `/runner/reviews/run` | may start agents | Review a pull request now, `{ project, number }` (`202`, with the review as started) |
| `GET` | `/runner/sandbox?fresh=1` | member | `{ available, reason, image, imageReady }`: whether Docker answers here, and the image sandboxed threads use |

**Memory.** `kind` is `decision`, `convention`, `fix` or `fact`; `text` is at most 1,000
characters, and a project keeps 500 at most. Threads' agents keep and find entries with Grid's
`memory_save` and `memory_search` tools. A new thread's first message carries, in a note before
it, the entries (up to eight, about 4,000 characters) that share the most words with that
message; each one given counts in `used`.

**Reviews.** With `enabled`, the runner lists the open pull requests of the project folder's
GitHub repository every three minutes, and each that is not a draft and was updated since
`since` gets a review of its head commit once: a thread (the review agent's `provider`, in its
read-only mode where it has one, as `ownerId`) whose message carries the pull request and its
diff, and whose reply is posted on the pull request as a comment. `POST /reviews/run` reviews one
again, as whoever asks. A review is stopped after 20 minutes.

**Sandboxes.** A thread created with `sandbox: true`, or in a project whose settings have
`sandbox: true`, has `sandbox: { image }`, and its agent runs as `docker run --rm` in that image,
seeing the thread's repository (and its worktree's git folder), the agent's own sign-in and
settings, and Grid's tools: nothing else of the machine. Creating one where Docker does not
answer is `409`; so is a turn in one when Docker has stopped since. The image is the machine's
`sandboxImage` (`PATCH /runner/machine`), or Grid's own `grid-sandbox` (`docker/sandbox`).

### Runner file attribution

Project Files listing, content and blame routes return live agent attribution only
when the latest edit's chat session belongs to the selected workspace. Linking the
same folder in two workspaces does not share thread IDs, titles or agent metadata.
A later edit by another workspace, or a removed session, leaves live attribution
empty; committed git authorship remains the repository's public history.

### Runner Operate

Operate uses the runner prefix `/runner` (and paired `/runner/env/:id`), bearer
authentication, `X-Grid-Workspace` selection and `{ data: ... }` responses.
A project must be linked on the selected machine in the selected workspace;
missing and foreign projects return `404`. Inherited object keys and invalid or
empty folder entries do not count as linked projects.

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `GET` | `/runner/operate/:project` | member | Service health and latest 200 incidents |
| `PUT` | `/runner/operate/:project/services/:name` | production | Register or change a service with `{ url }` (`204`) |
| `DELETE` | `/runner/operate/:project/services/:name` | production | Stop monitoring a service (`204`) |

The overview contains `project`, `intervalSeconds` (60), `allowed` (may manage
monitors), nullable `checkedAt`, `services`, and `incidents`. A service has `id`,
`name`, `url`, `state` (`healthy`, `degraded`, `down`, `unknown`), nullable
`checkedAt`, `responseMs`, `uptime`, `p95`, `incidentId`, and numeric `checks` and
`coverage`. Metrics cover the latest 24 hours: uptime is the percentage of
**observed checks** that succeeded, p95 covers successful responses, and coverage
is the percentage of minute slots actually checked. Unobserved time never counts
as healthy. Checks older than three minutes show `unknown`; stale latency is null.

Three consecutive failures open an incident and two consecutive successes resolve
it. A monitoring gap over three minutes resets the consecutive-check counters.
An incident has `id`, `serviceId`, `serviceName`, original `url`, `status` (`open`
or `resolved`), `openedAt`, nullable `resolvedAt`, and `monitoring`. Removing a
monitor or changing its URL stops monitoring its previous unresolved incident;
it stays open with `monitoring: false`, rather than falsely claiming recovery.
Transitions create stable, workspace-visible `incident_open` / `incident_resolved`
Inbox items linking to `/operate/:project?incident=:id`. A durable outbox retries
notification delivery after restart without duplicating the Inbox row.

Monitoring continues without a browser while the runner is running. For reliable
operation, keep the portable Grid bundle in a stable directory outside disposable
worktrees and run it under a restarting service. A stopped runner cannot observe
outages; missing checks remain unknown rather than counting as uptime. Persisted
Ship settings with public URLs are inherited automatically, without GitHub calls.
Manually configured monitors take precedence; removed monitors stay removed.
Addresses must be public HTTP/S endpoints, with no credentials, query or fragment.
DNS answers are checked and the connection pinned to a public address. Redirects
are not followed; only 2xx responses succeed. No response bodies or credentials
are retained. Up to 50 active services per machine are supported; names
are 1–80 characters and must be URL encoded in the path. PUT bodies over 4 KiB
return `413`, invalid names/addresses `400`, forbidden changes `403`, monitor limit
`409`, missing monitors `404`, and unsupported methods `405`. Checks and incident
records survive runner restart; history and operational Inbox rows are bounded.
Stopped services release active capacity. Tombstones for configured Ship sites
remain until those settings are removed; other stopped names are retained up to
200 per machine, with the oldest reclaimed. Ten concurrent probes keep the
supported 50-target timeout workload within the one-minute check interval.
Check timestamps identify the scheduled sampling round, so response latency does
not postpone the following round.


### Operate logs and costs

The same authentication, workspace selection, project-link boundary and `{ data }`
envelope apply. All log endpoints (including source listing) and all mutations
require `may(who, "production")`; costs overview is visible to project members.

| Method | Path (after `/runner`) | Response / input |
| --- | --- | --- |
| GET | `/operate/:project/logs` | `{ project, allowed: true, sources: [{ name, path }] }` |
| PUT | `/operate/:project/logs/:name` | `{ path }`, then `204` |
| GET | `/operate/:project/logs/:name` | `{ name, path, text, readAt, truncated, bytes, lines }` |
| DELETE | `/operate/:project/logs/:name` | `204` |
| GET | `/operate/:project/costs` | Costs overview below |
| POST | `/operate/:project/costs/charges` | `{ service, provider, amountCents, date }`, then `201 { data: charge }` |
| DELETE | `/operate/:project/costs/charges/:id` | `204` |

Names, services and providers are trimmed, 1–80 characters, with no slash,
backslash or control characters. Up to 20 named sources per project. Paths are
project-relative visible `.log` files, at most 1024 characters: absolute,
traversal, hidden and credential filenames, symlinks, nonregular and binary files
are refused. Registration validates the opened file; reads revalidate the opened
descriptor against the project root and current path to refuse replacement races.
The current implementation requires Linux `/proc/self/fd` and fails closed where
opened-file validation is unavailable. Reads use nonblocking flags and return at
most 64 KiB read and the latest 200 lines; a partial first line is dropped when
cut. `bytes` counts source bytes read before redaction/line limiting; `lines`
counts returned redacted lines. `truncated` covers either byte or line limiting.
Empty text is valid. ANSI/control sequences and common credential/PEM formats
are removed or redacted before plain text is returned. Redaction is best effort:
only configure logs intended for workspace production operators. Log text is
never persisted, included in diagnostics, or executed as shell commands.

The costs overview is `{ project, allowed, currency: "USD", agents, hosting }`.
`allowed` indicates production permission. `agents` has nullable `costUsd`,
`reportedSessions`, `totalSessions` and `providers`; each provider entry has
`provider` and those same three cost/coverage fields. Agent costs sum the maximum
valid non-negative numeric USD counter reported per **retained session**, matching
existing cumulative-counter semantics. SQL extracts only numeric usage metadata:
no messages, prompts or tools are materialized. This is a partial retained-session
reading, not a period invoice, token-price estimate or complete provider bill.
Invalid costs are excluded; unreported sessions remain in coverage totals. Null
means no reported costs; a reported zero stays zero. Provider totals use the same
null/zero semantics. Overflowing reported totals return `409`.

`hosting` has nullable `totalCents` and `charges`. A charge has `id`, `service`,
`provider`, `amountCents`, `date` and `createdAt`. Charges are manually recorded,
persisted USD amounts in non-negative integer cents up to `9007199254740991`;
aggregate totals must also stay within that safe integer range. `date` is a real
calendar date in `YYYY-MM-DD` format. No currency conversion or cloud billing
adapter is implied. No records means null; explicitly recording zero yields zero.
Up to 500 charges per project; exceeding capacity or total range returns `409`
instead of dropping financial records. Deletion releases capacity. Source metadata
and charges survive restart in the runner's chat database; log contents do not.

Malformed inputs return `400`, permission refusal `403`, missing sources/files,
charges or unlinked projects `404`, replacement races/limits `409`, unsupported
methods `405`, and JSON bodies above 4 KiB `413`. File errors return safe messages
without OS paths or exceptions. No provider adapter or health/reconnect behavior
changes are introduced by these endpoints.
